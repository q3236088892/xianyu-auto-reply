# 11 滑块验证失败与自动回复恢复复盘

## 1. 文档目的

本文记录 2026-07-23 一次"从闲鱼发送消息后没有自动回复"的排查过程。表面现象是自动回复失效，实际根因是账号 Token 无法刷新，而 Token 刷新被滑块验证（阿里 Baxia 风控）卡住。本文说明三层递进的根因、对应的修复动作、验证结果与日常维护注意事项。

本文不记录任何 Cookie 明文、Token 明文、密码或其他敏感凭据。

## 3. 故障现象

- 从闲鱼给该账号发送消息后，没有触发自动回复。
- 后台可见浏览器/命令行窗口不停打开又关闭。
- `logs/app/websocket.log` 中反复出现：

```text
Token刷新响应: {"ret": ["FAIL_SYS_USER_VALIDATE", "RGV587_ERROR::SM::哎哟喂,被挤爆啦,请稍后重试"], ...}
主引擎滑块未通过，启用 DrissionPage 兜底引擎重试
Baxia 滑块响应码: 300
Baxia 已拒绝当前轨迹
```

自动回复的前提是：账号 Token 能刷新成功 → WebSocket 长连接建立（`connected`）。本次链路卡在 Token 刷新，长连接一直无法就绪，所以消息进来也不会回复。

---

## 4. 根因分析（三层递进）

排查发现问题不是单一原因，而是三层依赖依次踩坑，修好一层才暴露下一层。

### 4.1 第一层：主引擎浏览器缺失（chromium-1228）

- 主滑块引擎 `common/services/captcha/slider_stealth.py` 使用 `state/deps` 里的 **playwright 1.61.0**，该版本要求 **chromium-1228**。
- 但 `runtime/playwright` 里只安装了给旧版 playwright 1.59.0 用的 **chromium-1217**。
- 报错：

```text
BrowserType.launch_persistent_context: Executable doesn't exist at
...\runtime\playwright\chromium-1228\chrome-win64\chrome.exe
```

- 主引擎连浏览器都起不来，直接掉进 DrissionPage 兜底引擎。

### 4.2 第二层：CDP 滑块被风控拒绝（code=300）

- chromium-1228 补装后，主引擎能起浏览器、能执行滑动，但滑块轨迹被判 `code=300`（拒绝）。
- 根因见 `common/services/captcha/real_mouse_slider.py` 头部注释：阿里 Baxia 能区分 **CDP 注入的鼠标事件** 与 **真实硬件鼠标事件**。Playwright(CDP) 即使回放真人轨迹也被判 300；用物理光标（SendInput / pyautogui）回放同一条轨迹则 code=0 通过。
- 当时系统设置 `captcha.slider_mode = browser`（CDP 模式），注定过不了。

### 4.3 第三层：real_mouse 引擎找不到系统 Chrome

- 切换到 `captcha.slider_mode = real_mouse` 后，引擎成功启用，但报错：

```text
Chromium distribution 'chrome' is not found at
C:\Users\Administrator\AppData\Local\Google\Chrome\Application\chrome.exe
```

- 根因见 `real_mouse_slider.py` 的 `init_browser`：该引擎**刻意**使用 `channel="chrome"`（本机真实 Google Chrome，指纹更自然），而非项目自带 chromium。而这台机器从未安装过 Google Chrome。

## 5. 修复动作

| # | 层级 | 动作 | 说明 |
|---|------|------|------|
| 1 | 主引擎浏览器 | 用 `state/deps` 的 playwright 1.61.0 CLI 下载 **chromium-1228** 到 `runtime/playwright` | 完整版 chrome.exe + headless shell |
| 2 | 滑块模式 | 系统设置 `captcha.slider_mode`：`browser` → `real_mouse` | 直接改数据库 `xy_system_settings`；websocket 每次滑块前调用 `refresh_slider_mode_from_database()` 实时读取，无需重启 |
| 3 | real_mouse 依赖 | 确认 `pyautogui 0.9.54` 已在 `state/deps`（本就随包安装），无需额外安装 | `win_input` 用纯 ctypes 调 SendInput，不依赖 pywin32 |
| 4 | real_mouse 浏览器 | 安装官方 **Google Chrome**（企业版 MSI）到默认路径 `C:\Program Files\Google\Chrome\Application\chrome.exe` | 满足引擎 `channel="chrome"` 要求 |

关键配置项（`xy_system_settings` 表）：

```text
captcha.slider_mode = real_mouse
```

## 7. 日常维护注意事项

1. **real_mouse 会接管物理鼠标 2~3 秒**：每次过滑块时，程序用物理光标回放真人轨迹，期间不要移动鼠标。这是它能过风控（code=0）的原理，属正常现象。
2. **依赖系统 Google Chrome**：real_mouse 模式必须保留系统安装的 Google Chrome（默认路径）。若卸载或路径变动，引擎会回到"找不到 chrome"报错。
3. **不要把 slider_mode 改回 browser**：CDP 模式在当前风控下几乎必被 code=300 拒绝。
4. **playwright 版本与 chromium revision 要匹配**：若将来升级 `state/deps` 里的 playwright，需要同步补装对应 revision 的 chromium 到 `runtime/playwright`（用该 playwright 自己的 CLI 下载）。可查 `playwright/driver/package/browsers.json` 里的 chromium revision。
5. **账号 2232648246 的登录/扫码/过验证由用户手动执行**：程序只做诊断与配置。
