## 3. 故障现象

管理页面曾显示：

```text
登录恢复退避中，暂不可接管
密码登录失败退避中，剩余599.8秒
```

或显示：

```text

重连中
最近连接成功：暂无记录
```

表面现象是消息不能自动回复，但实际上存在两个不同阶段的问题：

1. 登录 Token 选择错误，导致连接无法正常建立。
2. 连接恢复后，第一次测试使用了错误的商品和会话身份，因此程序按安全规则跳过回复。

## 4. 根因一：同名 Cookie 存在多个存储上下文

### 4.1 实际情况

浏览器资料中存在两组同名 Cookie：

```text
_m_h5_tk
_m_h5_tk_enc
```

其中：

- 一组是普通、非分区 Cookie；
- 一组带有 `partitionKey=https://goofish.com`；
- 两组名称相同，但属于不同的浏览器存储上下文，因此可以同时存在；
- 普通 Cookie 组合验证时返回 Token 过期；
- 带正确 `partitionKey` 的组合验证时返回成功。

### 4.2 为什么浏览器允许同名 Cookie

Cookie 不能只用名称识别。完整身份通常还包括：

- `name`
- `domain`
- `path`
- `partitionKey`
- 是否为 host-only Cookie
- 安全、SameSite 和过期属性

因此，两个名称相同的 Cookie 不一定是重复垃圾数据。浏览器可以根据分区上下文把它们当成两条独立记录。

### 4.3 程序为什么会选错

旧逻辑可能将 Cookie 简化为单值字典：

```python
cookies[cookie_name] = cookie_value
```

这种处理会丢失 `domain`、`path` 和 `partitionKey`。当同名 Cookie 有多份时，最终留下哪一份取决于遍历或覆盖顺序，程序可能选中已过期的普通 Cookie。

本次直接后果为：

```text
选中失效 Cookie
→ Token 刷新返回令牌过期
→ 登录恢复失败
→ 进入约 600 秒退避
→ WebSocket 暂时无法接管
→ 无法接收并处理正常聊天消息
```

### 4.4 本次临时修复

已执行：

1. 从账号专属浏览器资料中识别普通 Cookie 和分区 Cookie。
2. 分别进行有效性验证。
3. 将验证成功的分区 Cookie 组合写入数据库。
4. 同步浏览器中的其他最新必要 Cookie。
5. 重启并验证 Token 刷新、WebSocket 初始化和心跳。

数据库操作前已保留备份：

```text
app\data\xianyu_data.db.before-partitioned-cookie-fix.bak
```

本次没有清空业务数据，也没有修改 Cookie 以外的订单、卡密或回复配置。

## 5. 根因二：第一次测试时账号处于买家身份

第一次测试消息为：

```text

```

对应商品：

```text

```

系统查到该商品卖家是账号 `2211979199459`，而运行自动回复的是账号 `2232648246`。因此，在该会话里自动回复账号是买家，不是卖家。

程序按防误回复规则执行：

```text
商品非本账号所有
→ 本账号为买家身份
→ 跳过自动回复
```

这不是连接再次失败，而是程序正确阻止买家账号对卖家自动回复。

此外，消息“测试自动回复123”也没有对应关键词，并且当时没有启用可覆盖该消息的默认回复。即使商品身份正确，这句话也不会命中当前商品关键词规则。

## 7. 当前修复的边界

当前故障已经恢复，但目前主要是数据和运行状态层面的修复，并未确认源码已经具备“多份同名 Cookie 自动选择”能力。

因此：

- 当前可以正常使用；
- 浏览器以后重新登录、滑块验证或刷新 Cookie 时，可能再次出现普通 Cookie 与分区 Cookie 并存；
- 如果旧代码仍只按名称读取 Cookie，理论上仍有复发可能；
- 要永久降低复发概率，需要实施第 9 节的程序级加固。

## 8. 用户侧日常防范规范

### 8.1 使用专属浏览器资料

账号 `2232648246` 只使用：

```text
browser_data\user_2232648246
```

不要让自动回复程序和普通 Edge 同时使用该目录，也不要在普通 Edge 中长期重复登录同一自动回复账号。

### 8.2 验证必须在账号专属窗口完成

需要滑块、短信或其他人工验证时：

1. 使用程序为该账号打开的专属浏览器窗口；
2. 在真实闲鱼登录页面完成验证；
3. 验证完成后等待程序自动刷新 Token；
4. 不要反复打开无效 Token 接口地址；
5. 不要连续多次登录或连续触发滑块。

### 8.3 不要手动按名称复制 Cookie

不要只复制：

```text
_m_h5_tk=...
_m_h5_tk_enc=...
```

这样会丢失分区、域名和路径信息。必须由程序从浏览器上下文读取并验证完整 Cookie 组合。

### 8.4 避免错误测试

测试自动回复时必须满足：

1. 从其他买家账号操作；
2. 打开自动回复账号自己发布的商品；
3. 从该商品页面点击“我想要”进入会话；
4. 发送已经配置的关键词；
5. 不要在自动回复账号作为买家的会话中测试卖家自动回复。

### 8.5 保证电脑持续运行

自动回复依赖本机服务和网络：

- 电脑不能睡眠或休眠；
- 网络需要保持连接；
- `START.cmd` 启动的服务必须持续运行；
- `127.0.0.1:8090` 应保持监听；
- 不要随意结束受管 Python 进程。

## 9. 程序级永久加固方案

### 9.1 加固目标

程序不能再假设“一个 Cookie 名称只有一个值”。必须做到：

1. 完整保留 Cookie 的上下文属性；
2. 自动识别同名 Cookie 的多个候选；
3. 通过真实接口验证候选组合；
4. 仅持久化验证成功的组合；
5. 当前组合失效时自动尝试其他候选；
6. 所有候选都失效后才进入人工登录流程；
7. 任何日志都不输出 Cookie 明文。

### 9.2 Cookie 数据模型

不要使用：

```python
Dict[str, str]
```

建议使用保留完整属性的结构：

```python
class CookieCandidate:
    name: str
    value: str
    domain: str
    path: str
    partition_key: str | None
    host_only: bool
    secure: bool
    http_only: bool
    same_site: str | None
    expires_at: float | None
```

候选 Cookie 的唯一键至少应为：

```text
(name, domain, path, partitionKey, hostOnly)
```

### 9.3 Token Cookie 配对

`_m_h5_tk` 与 `_m_h5_tk_enc` 必须来自兼容的上下文，不能把普通 Cookie 和分区 Cookie 混合配对。

建议按以下字段分组：

```text
(domain, path, partitionKey)
```

每组必须同时包含：

```text
_m_h5_tk
_m_h5_tk_enc
```

缺少任意一个时不得作为完整候选参与验证。

### 9.4 候选选择顺序

建议优先级：

1. 上次验证成功、尚未明显过期的候选；
2. `partitionKey=https://goofish.com` 的完整候选；
3. 与当前顶级页面和目标接口上下文一致的候选；
4. 其他完整候选；
5. 所有候选失败后再触发人工登录。

优先级只用于减少请求次数，最终必须以接口验证结果为准，不能仅凭时间或 Cookie 类型判断有效。

### 9.5 主动有效性验证

对每个候选组合调用现有的无副作用 Token 验证或刷新流程：

```text
候选 A → 验证成功 → 选中并停止
候选 A → 明确 Token 过期 → 尝试候选 B
候选 A → 网络超时 → 标记网络异常，不立即删除候选
所有候选 → 明确鉴权失败 → 请求人工登录
```

必须区分：

- Token 过期；
- 风控或滑块；
- 网络超时；
- DNS/代理异常；
- 服务端临时错误；
- Cookie 缺失或格式错误。

网络错误不能被误判为密码错误，也不应立即进入长时间密码登录退避。

### 9.6 原子持久化与回滚

验证成功后再更新数据库，推荐流程：

```text
读取当前数据库 Cookie
→ 保存 last-known-good 快照
→ 验证新候选
→ 开启数据库事务
→ 写入完整新 Cookie
→ 提交事务
→ 再次验证 Token
→ 失败则恢复 last-known-good
```

禁止先覆盖数据库、再验证是否可用。

如果当前数据库无法保存 `partitionKey` 等结构化信息，可增加独立字段或新表，例如：

```text
cookie_candidate_sets
- account_id
- cookie_json_encrypted
- partition_key
- token_hash
- verified_at
- expires_at
- status
```

原有 `cookies.value` 可继续保存程序最终使用的 Cookie Header，但不能作为唯一来源。

### 9.7 运行时自动恢复

运行过程中检测到明确 Token 过期时：

1. 暂停新消息发送；
2. 保留消息接收队列和待处理状态；
3. 重新读取浏览器 Cookie 候选；
4. 逐组验证；
5. 找到有效候选后刷新 Token；
6. 重建 WebSocket；
7. 心跳成功后恢复处理；
8. 所有候选均失败才提示人工验证。

禁止在第一组 Cookie 失败后立即进入 600 秒密码登录退避。

### 9.8 登录状态机加固

建议使用明确状态：

```text
DISCONNECTED
COOKIE_DISCOVERY
TOKEN_VALIDATING
TOKEN_READY
WEBSOCKET_CONNECTING
CONNECTED
MANUAL_VERIFICATION_REQUIRED
LOGIN_BACKOFF
```

状态切换要求：

- `CONNECTED` 必须以 Token 成功、WebSocket 初始化成功和至少一次心跳成功为依据；
- 进入 `LOGIN_BACKOFF` 前必须确认所有 Cookie 候选均已失败；
- 恢复连接后必须清理旧的“登录恢复退避中”提示；
- 页面展示状态必须来自当前运行状态，不能长期显示历史错误缓存。

### 9.9 浏览器资料互斥锁

同一账号浏览器目录同时只能被一个自动化实例控制。

建议在：

```text
browser_data\user_2232648246
```

旁建立账号级锁文件，内容包含：

- PID；
- 启动时间；
- 应用实例标识；
- 浏览器资料绝对路径。

启动新实例前检查锁和 PID；只有确认旧进程不存在时才回收过期锁，防止两个实例同时刷新和覆盖 Cookie。

### 9.10 日志和监控

允许记录：

- Cookie 名称；
- 域名；
- Path；
- 是否分区；
- `partitionKey`；
- 过期时间；
- Cookie 值的不可逆短哈希；
- 候选序号；
- 验证结果分类。

禁止记录：

- Cookie 明文；
- 完整 Token；
- 密码；
- 验证码；
- AI Key；
- 可直接复用的请求头。

推荐日志示例：

```text
发现 2 组 Token Cookie 候选
候选 1: partitioned=false, token_hash=********, result=TOKEN_EXPIRED
候选 2: partitioned=true, partitionKey=https://goofish.com, token_hash=********, result=SUCCESS
已选用候选 2，准备刷新 WebSocket
```

### 9.11 自动回复规则校验

连接正常不等于一定会回复。收到消息后还要依次确认：

```text
是否为聊天正文
→ 是否为买家发给本账号
→ 商品是否属于本账号
→ 会话是否处于暂停或黑名单状态
→ 是否命中关键词、商品回复、默认回复或 AI 回复
→ 是否允许发送
```

管理页面建议增加“为什么没有回复”的可见原因，例如：

```text
跳过：本账号为买家
跳过：商品不属于本账号
跳过：未命中关键词且默认回复未开启
跳过：会话处于人工暂停期
失败：Token 已过期
失败：发送接口风控
```

## 12. 再次出现故障时的应急流程

### 第一步：不要反复登录

不要连续输密码、连续做滑块或反复打开登录 Token 地址，以免触发更长退避或风控。

### 第二步：检查服务

```powershell
Get-NetTCPConnection -LocalPort 8090 -ErrorAction SilentlyContinue
```

确认监听进程后再检查该 PID 的命令行，避免误结束其他程序。

### 第三步：检查关键日志

重点搜索：

```text
Token刷新成功
WebSocket初始化完成
开始监听WebSocket消息
心跳响应正常
FAIL_SYS_TOKEN_EXOIRED
登录恢复退避
本账号为买家身份
关键词匹配成功
关键词发出
```

### 第四步：区分连接问题与规则问题

- 没有 Token 成功、WebSocket 或心跳：连接问题；
- 有心跳、能收到正文，但显示买家身份：测试商品或账号方向错误；
- 有心跳、商品属于本账号，但未命中规则：回复配置问题；
- 已记录“关键词发出”，买家未收到：发送接口、风控或客户端同步问题。

### 第五步：处理 Cookie 候选

## 13. 最终结论

本次故障不是单一问题：

1. 登录连接阶段，程序在同名普通 Cookie 和分区 Cookie 中选中了失效组合；
2. 连接恢复后的第一次测试，又因为自动回复账号在目标商品中是买家而被安全规则跳过；
3. 使用本账号商品和已配置关键词重新测试后，消息接收、规则匹配和自动发送均已验证成功。

当前系统可以正常使用。要长期杜绝同类登录故障，核心不是删除同名 Cookie，而是让程序完整识别 Cookie 上下文、主动验证多组候选、保存 last-known-good，并在所有候选都失败后才进入人工登录退避。
